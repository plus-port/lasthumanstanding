# 0001 — Astro SSR on Node with Drizzle and libSQL

Date: 2026-09-15
Status: accepted

## Context

Six features, one team, six weeks, no existing system. The stack was chosen as Astro. Managers need live readiness answers, so pages render per request rather than at build time.

## Decision

- Astro 7 with `output: 'server'` and the `@astrojs/node` standalone adapter.
- Drizzle ORM over `@libsql/client`; a local SQLite file in development, a libSQL URL when deployed. Migrations generated by drizzle-kit into `drizzle/`.
- Vitest for unit tests, `astro check` for types, ESLint with `eslint-plugin-astro`, Prettier with `prettier-plugin-astro`. All run through `pnpm gate`.
- No UI framework island until a component needs client state. Astro components and Actions first.

## Alternatives rejected

- Static output with client-side fetching — readiness is per request and per manager; pre-rendering buys nothing.
- Astro DB — ties the schema to one hosting path; Drizzle keeps the SQL and the option to move to Postgres.
- Postgres from day one — an extra service to run for 600 rows of employees; not needed within the six-week window.

## Consequences

- One language and one toolchain; the whole gate is `pnpm gate`.
- SQLite is single-writer. Revisit if concurrent writes from 8 sites cause lock contention; the move is a driver swap plus a decision record.
- Every schema change ships with a migration in the same commit.
